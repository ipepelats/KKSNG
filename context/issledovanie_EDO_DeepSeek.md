### 📚 Отправки пакетов документов по ЭДО через роуминг

Для успешной разработки важно чётко понимать, с какими типами данных мы работаем и какова архитектура их обмена.

*   **Роуминг в ЭДО**: Это технология, обеспечивающая юридически значимый обмен электронными документами между организациями, которые подключены к разным операторам ЭДО (например, 1С-ЭДО, Контур.Диадок, СБИС). Это ключевая функция для взаимодействия со всеми контрагентами, независимо от их выбора платформы.

*   **Формализованный документ (ФНС)**: Это электронный документ в формате XML, структура и содержание которого строго регламентированы приказами ФНС России. Он является машиночитаемым и предназначен для автоматической обработки как учётными системами, так и самими налоговыми органами.
    *   **Примеры**: Счёт-фактура, УПД (универсальный передаточный документ), ТОРГ-12, Акт выполненных работ в XML-формате.
    *   **Юридическая значимость**: Для таких документов формат XML является обязательным условием для признания их юридически значимыми и для предоставления в ФНС без бумажного дубликата.

*   **Неформализованный документ (свободный формат)**: Это документ, для которого ФНС не утверждён строгий формат. Он может быть в любом удобном виде, например, PDF, DOC, XLSX, JPEG. Он подписывается электронной подписью (УКЭП), что придаёт ему юридическую силу, но его содержимое не подлежит автоматизированному анализу со стороны ФНС.
    *   **Примеры**: Договор, счёт на оплату (если не в XML), информационное письмо, спецификация, техническое задание.

*   **Пакет (или транспортный контейнер)**: Это единый контейнер (обычно zip-архив), в котором пересылается один или несколько электронных документов (как формализованных, так и неформализованных) от отправителя к получателю за одну транзакцию.

### 🗂️ Принципы объединения документов в пакет

Отправка документов пакетом — это логичная операция, особенно в рамках одной сделки. Однако существуют чёткие правила, которые необходимо соблюдать.

#### Регламентированные варианты состава пакета

Операторы ЭДО придерживаются определённых регламентов, определяющих допустимый состав пакетов. Наиболее полная классификация, которую удалось найти, включает **5 вариантов**:

1.  **Основной документ: Счёт-фактура (или УПД с функцией СЧФ)**
    *   **Дополнительно может включать**: Документ с функцией ДОП (дополнительные сведения) или ТОРГ-12, или Акт + один или несколько неформализованных документов.

2.  **Основной документ: Документ с функцией СЧФДОП**
    *   **Дополнительно может включать**: Один или несколько неформализованных документов.

3.  **Основной документ: Документ с функцией ДОП**
    *   **Дополнительно может включать**: Счёт-фактура (УПД с функцией СЧФ) + один или несколько неформализованных документов.

4.  **Основной документ: ТОРГ-12 или Акт**
    *   **Дополнительно может включать**: Счёт-фактура (УПД с функцией СЧФ) + один или несколько неформализованных документов.

5.  **Основной документ: Неформализованный документ**
    *   **Дополнительно может включать**: Один или несколько других неформализованных документов. В этом пакете один из неформализованных документов назначается основным.

#### Ограничения и ключевые правила

*   **Максимальный размер пакета**: Общий объём транспортного контейнера не должен превышать **70 МБ**.
*   **Максимальное количество документов**: В один пакет можно объединить **до 30 документов**.
*   **Один счёт-фактура в пакете**: Согласно общему правилу, в одном пакете не может быть более одного счёта-фактуры.
*   **Основной документ**: Один из документов в пакете всегда является "основным". Именно его регламент определяет порядок обработки и жизненный цикл всего пакета (например, ожидание подписания получателем).
*   **Обработка ответных пакетов**: Ответный пакет (например, с подписью получателя) формируется только в том случае, если основной документ в исходном пакете требует подписания (имеет атрибут `ResignRequired="true"`). В ответном пакете будут перечислены все документы, для которых была запрошена подпись.

### ⚙️ Технические аспекты реализации

Для разработки интеграции с ЭДО через роуминг критически важно понимать внутреннее устройство пакета.

#### Структура транспортного контейнера (пакета)

Транспортный контейнер, как правило, представляет собой zip-архив, внутри которого находится:

*   **Файл описания содержимого пакета (metadata.xml)**: Это обязательный XML-файл, который служит "оглавлением" пакета. Его структура описана в нормативных документах.
    *   **Корневой узел `пакет`** с атрибутами: `версияФормата`, `типДокументооборота`, `идентификаторДокументооборота`, `типТранзакции`.
    *   **Узлы**: `отправитель`, `получатель`, `системаОтправителя`, `системаПолучателя`.
    *   **Дочерние узлы `документ`** (множественные), описывающие каждый вложенный документ, с атрибутами:
        *   `идентификаторДокумента` — уникальный ID документа.
        *   `типДокумента` — тип документа (например, `СчетФактура`, `УПД`, `Неформализованный`).
        *   `типСодержимого` — MIME-тип (по умолчанию `xml`, для PDF это `application/pdf`).
        *   `сжат` — булево значение, сжат ли документ.
        *   `зашифрован` — булево значение, зашифрован ли документ.
        *   `исходноеИмяФайла` — исходное имя файла (необязательный атрибут).
*   **Файлы документов**: Это сами документы в форматах XML (для формализованных) или любых других (для неформализованных). Их имена могут быть стандартизированы (например, `digital.xml` для основного формализованного документа) или быть произвольными, но тогда их соответствие описано в `metadata.xml`.

#### Взаимодействие с API операторов ЭДО

API операторов ЭДО предоставляют методы для отправки и получения таких пакетов. Ключевые методы, которые вам потребуется изучить в документации выбранного оператора:

*   **Отправка пакета**: Метод, принимающий на вход транспортный контейнер и возвращающий идентификатор документооборота (`docflow ID`).
*   **Получение входящих документов/пакетов**: Метод для опроса ящика на предмет новых поступлений. Обычно возвращает список идентификаторов документооборотов.
*   **Получение конкретного пакета**: Метод, принимающий `docflow ID` и возвращающий транспортный контейнер.
*   **Подписание документа/пакета**: Метод для отправки подписанного документа или пакета обратно отправителю. Важно, что для неформализованных документов подпись может быть оформлена отдельно.
*   **Методы для работы с роумингом**: API для отправки/принятия приглашений контрагентам для настройки роуминга.

#### Жизненный цикл пакета в роуминге

1.  **Формирование**: Отправитель формирует транспортный контейнер с `metadata.xml` и файлами документов.
2.  **Подписание и отправка**: Контейнер подписывается УКЭП отправителя и передаётся через API своему оператору ЭДО.
3.  **Маршрутизация**: Оператор-отправитель передаёт пакет оператору-получателю через роуминговый шлюз. Каждый оператор может взимать свою комиссию за обработку.
4.  **Доставка и проверка**: Оператор-получатель доставляет пакет в ящик конечного получателя, где тот может его просмотреть и проверить.
5.  **Подписание получателем**: Получатель подписывает документ(-ы) (обычно основной документ пакета) своей УКЭП и отправляет подпись обратно.
6.  **Завершение**: Обе стороны получают подтверждения (извещения) о завершении документооборота, и пакет считается юридически значимым.

### 📝 Юридическая значимость и нормативная база

*   **Формализованные документы**: Их юридическая сила напрямую зависит от соответствия формату, утверждённому приказами ФНС. Наиболее актуальные приказы для вашей разработки:
    *   **Счёт-фактура (новый формат)**: Приказ ФНС России от 19.12.2018 N ММВ-7-15/820@.
    *   **Документ о передаче результатов работ (об оказании услуг)**: Приказ ФНС России от 30.11.2015 N ММВ-7-10/552@.
    *   **Документ о передаче товаров при торговых операциях**: Приказ ФНС России от 30.11.2015 N ММВ-7-10/551@.
    *   **Универсальный передаточный документ (УПД)**: Формат 5.03, утверждённый приказом ФНС России от 19.12.2023 N ЕД-7-26/970@.
*   **Неформализованные документы**: Юридическая сила обеспечивается наличием квалифицированной электронной подписи (УКЭП). Однако стоит помнить, что при истребовании ФНС такие документы, возможно, придётся предоставлять в виде заверенных бумажных копий.

### 💡 Практические рекомендации по разработке

1.  **Начните с выбора оператора ЭДО**: Изучите документацию API нескольких ведущих операторов (Контур.Диадок, 1С-ЭДО, СБИС, Такском). Выберите того, чей API и условия роуминга лучше всего соответствуют вашим задачам.
2.  **Реализуйте формирование `metadata.xml`**: Это центральная часть вашего решения. Необходимо разработать генератор этого файла, который будет корректно заполнять все атрибуты для каждого документа в пакете.
3.  **Обеспечьте работу с XML-схемами**: Для формализованных документов вам потребуется валидация сгенерированных XML-файлов по XSD-схемам, предоставляемым ФНС. Это гарантирует их корректность.
4.  **Внедрите подписание**: Интегрируйте библиотеки для работы с УКЭП (например, КриптоПро) для подписания как самого пакета, так и отдельных документов внутри него.
5.  **Разработайте надёжную систему обработки статусов**: Ваша система должна корректно отслеживать все стадии документооборота: отправлен, доставлен, получен, подписан, отклонён и т.д.
6.  **Продумайте обработку ошибок**: Особенно в части валидации XML-схем и ошибок от API оператора ЭДО. Подготовьте понятные пользователю сообщения об ошибках.
